# Solana Pay Technical Specification

## 1. Introduction
Solana Pay is an open, decentralized payment standard built on the Solana blockchain. It enables merchants to accept instant, direct cryptocurrency payments with near-zero fees. Designed with Point-of-Sale (POS) systems and autonomous agent ecosystems in mind, the protocol is stateless, relying entirely on the blockchain as the source of truth for payment verification.

## 2. The URI Scheme
The core of Solana Pay is its standardized URI scheme, which encodes payment requests. This URI can be presented as a QR code or transmitted over HTTP (such as in an HTTP 402 Payment Required payload).

**Format:**
`solana:<recipient>?amount=<amount>&reference=<reference>&label=<label>&message=<message>&memo=<memo>`

### 2.1 URI Parameters
*   **`recipient`** (Required): The base58-encoded public key of the merchant's token account or native SOL wallet.
*   **`amount`** (Optional but recommended): The transaction value. Must be a non-negative integer or decimal. If omitted, the wallet prompts the user to specify an amount.
*   **`reference`** (Highly Recommended): A unique 32-byte public key generated by the merchant for this specific transaction. It acts as a stateless idempotency key.
*   **`label`** (Optional): URL-encoded merchant or store name (e.g., `SES%20Tollgate`).
*   **`message`** (Optional): URL-encoded description of the purchase.
*   **`memo`** (Optional): A string to be included in the SPL Memo program instruction.

## 3. Payment Verification Flow
Since Solana Pay does not use webhooks or traditional backends, validation is entirely on-chain.

### Step 3.1: Generate a Reference
The merchant generates a unique Keypair to serve as the `reference`. The public key is embedded in the URI. The private key is immediately discarded, as it is only used for indexing.

### Step 3.2: Listen for Transactions
The merchant polls the Solana RPC network using `getSignaturesForAddress`, querying the `reference` public key.

```javascript
// TypeScript Example
const signatures = await connection.getSignaturesForAddress(referencePublicKey, { limit: 1 });
if (signatures.length > 0) {
    const signature = signatures[0].signature;
    // Proceed to verification
}
```

### Step 3.3: Validate the Transaction
Once a signature is found, fetch the transaction details using `getTransaction`.
The verification server MUST validate the following conditions:
1.  **Recipient Match:** The destination token account matches the merchant's expected account.
2.  **Amount Match:** The pre-balance and post-balance of the merchant's account show an increase exactly equal to the requested `amount`.
3.  **Mint Match:** The token mint matches the expected asset (e.g., USDC Mint `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v`).
4.  **No Errors:** The transaction `meta.err` is `null`.

## 4. Integration with Autonomous Agents (x402 Protocol)
When an autonomous agent attempts to access a paid resource, the server intercepts the request and responds with an `HTTP 402 Payment Required`. 

The response body contains a JSON payload mapping to the Solana Pay specification:
```json
{
  "error": "Payment required",
  "payment_protocol": "x402",
  "amount": "0.001",
  "asset": "USDC",
  "network": "solana",
  "merchant_address": "7x...9q",
  "reference": "unique-32-byte-key-base58"
}
```
The agent dynamically constructs the Solana Pay transaction, signs it with its embedded wallet, broadcasts it to the RPC, and retries the HTTP request including the transaction signature in the `X-Payment-Proof` header.
